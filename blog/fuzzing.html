Fuzzing과 Fuzzer — 개념 및 차이점

2025. 06
Fuzzing AFL++ Jackalope 보안테스트 취약점분석

퍼징(Fuzzing)은 프로그램에 무작위·예상치 못한 입력을 자동으로 대량 주입해 크래시·취약점을 찾는 보안 테스트 기법이다. Fuzzer는 이 과정을 자동으로 수행해주는 도구이며, 현재 Coverage-Guided Fuzzing이 업계 표준 방식으로 자리잡았다.

🔍

Fuzzing이란?

퍼징(Fuzzing)은 소프트웨어나 시스템에 무작위 또는 예상치 못한 데이터를 자동으로 대량 입력하여, 프로그램이 크래시(비정상 종료)되거나 오류를 일으키는 지점을 찾아 잠재적인 보안 취약점을 발견하는 테스트 기법이다.

보통 자동화 도구를 활용해 수많은 입력값을 빠르게 주입하고, 그 과정에서 프로그램의 예외 상황이나 보안 취약점을 관찰한다. 하드웨어·소프트웨어 모두에 적용 가능하다.

동작 흐름

1. 입력 생성 → 무작위 또는 변형된 데이터 생성 2. 프로그램 실행 → 타겟 프로그램에 주입 3. 결과 모니터링 → 크래시 / 오류 / 이상 동작 감지 4. 반복 → 수백만~수십억 회 자동 반복

왜 쓰냐?

사람이 직접 테스트하면 "정상적인 경우"만 생각하게 된다. 하지만 공격자는 개발자가 전혀 생각 못 한 이상한 입력을 넣는다. Fuzzer는 그 이상한 입력을 사람 대신 무한히 자동으로 생성해준다.

특히 효과적인 분야

  • 보안 (Security): 신뢰할 수 없는 외부 입력을 처리하는 소프트웨어의 취약점 발견
  • 정확성 (Correctness): 복잡한 두 알고리즘이 동일한 결과를 생성하는지 검증
  • 안정성 (Stability): 복잡한 입력을 처리하는 API가 대량 입력에서도 안정적으로 동작하는지 확인
개발자는 보통 메모리 누수·버퍼 오버플로 같은 오류를 탐지하는 테스트를 직접 작성하지 않는다. 하지만 이것들이 실제 보안 취약점과 시스템 장애의 주요 원인이 된다. 퍼징은 실제 서비스 환경에서 발생하기 전에 이를 미리 발견할 수 있게 해준다.
📂

Fuzzing의 종류

Fuzzing은 입력 데이터를 어떻게 생성하느냐에 따라 크게 세 가지로 나뉜다.

① Mutation-Based Fuzzing (변이 기반 퍼징)

Dumb Fuzzing이라고도 불린다. 기존 입력 파일(Seed)을 기반으로 랜덤하게 데이터를 변형(Mutate)하여 새로운 테스트 케이스를 생성하는 방식이다.

  • 입력 포맷에 대한 사전 지식이 없어도 됨
  • 랜덤하게 바이트를 삽입, 삭제, 치환함
  • 구조가 복잡한 파일 포맷에는 잘 작동하지 않지만, 단순한 프로그램이나 에러 핸들링이 약한 코드에서는 효과적
  • 대표 도구: AFL, Radamsa, zzuf

② Generation-Based Fuzzing (생성 기반 퍼징)

Smart Fuzzing이라고도 불린다. 입력 포맷의 구조(Grammar, Protocol 등)를 이해한 후, 유효하고 의미 있는 입력을 직접 생성하는 방식이다.

  • 파일 포맷, 프로토콜, API 구조 등을 모델링한 후 그에 따라 입력 생성
  • 포맷이 까다로운 입력(JSON, PNG, PDF, HTTP 등)에 유리
  • 구조화된 입력 덕분에 깊은 코드 경로 탐색 가능
  • 대표 도구: Peach Fuzzer, BooFuzz, Domato(웹용 DOM 퍼저)

③ Guided-Based Fuzzing (피드백 기반 퍼징)

Coverage-Guided Fuzzing이라고도 불린다. 테스트 실행 후 얻은 커버리지, 경로 정보를 피드백으로 받아 다음 테스트 케이스 생성에 반영하는 방식이다. 현대 퍼저의 표준 방식으로 자리잡았다.

  • 실행 중 새로운 분기 경로에 도달했는지 여부로 입력을 평가
  • 더 많은 커버리지를 확보할 수 있도록 입력을 점진적으로 진화시킴
  • 효과적인 취약점 탐지에 매우 유리
  • 대표 도구: AFL++, WinAFL, libFuzzer, Honggfuzz, Syzkaller(커널 퍼징)
종류별칭입력 생성 방식특징
Mutation-BasedDumb Fuzzing기존 입력 변형간단하지만 복잡한 포맷엔 비효율
Generation-BasedSmart Fuzzing포맷 모델 기반 생성구조적 입력에 강함
Guided-BasedCoverage-Guided커버리지 피드백 반영현재 가장 많이 쓰이는 표준 방식

+ 보너스: Sanitizer

Fuzzing과 함께 사용하는 버그 탐지 보조 도구다. Fuzzer는 크래시가 발생해야 버그를 발견했다고 판단하는데, 보안상 중요한 버그 중에는 즉시 크래시를 일으키지 않는 경우도 많다. Sanitizer를 함께 사용하면 숨겨진 버그도 크래시로 변환시켜 탐지가 쉬워진다.

  • AddressSanitizer (ASan): Use-After-Free, 버퍼 오버플로우 등 메모리 안전성 문제 탐지. Fuzzing 시 거의 필수.
  • UndefinedBehaviorSanitizer (UBSan): 정수 오버플로우, 잘못 정렬된 포인터 등 정의되지 않은 동작 탐지.
  • MemorySanitizer (MSan): 초기화되지 않은 메모리 읽기 탐지. 매우 유용하나 설정이 복잡함.
핵심: Fuzzer = 이상한 입력을 던지는 도구 / Sanitizer = 그 입력으로 생긴 숨은 버그까지 잡아주는 도구. 둘을 같이 써야 효과가 극대화된다.
🛠

Fuzzer란?

퍼저(Fuzzer)는 소프트웨어나 시스템의 취약점을 찾기 위해 무작위, 유효하지 않거나 예기치 않은 데이터를 프로그램의 입력값으로 지속적으로 주입하는 도구다. 이 과정을 통해 프로그램이 비정상적으로 종료(크래시)되거나 보안 결함이 발생하는지 자동으로 확인한다.

Fuzz Target이란?

Fuzzer가 실제로 입력을 던지는 대상 함수다. 바이트 배열(Byte Array)을 입력받아 테스트 대상 API에 전달하는 역할을 한다. 퍼징 엔진은 같은 프로세스 안에서 수백만~수십억 번 입력을 반복 실행하기 때문에, Fuzz Target은 아래 조건을 만족해야 효율적으로 동작한다.

좋은 Fuzz Target의 조건

  • 모든 입력을 처리할 수 있어야 함: 빈 입력, 매우 큰 입력, 잘못된 입력, 손상된 입력이 들어와도 정상 동작해야 한다.
  • exit() / abort() 사용 금지: 입력에 의해 이런 함수가 호출되면 버그로 간주된다.
  • 결정적(Deterministic)이어야 함: 같은 입력이면 항상 같은 결과가 나와야 한다. rand() 같은 랜덤 값은 퍼징 효율을 크게 떨어뜨린다.
  • 빠르게 실행되어야 함: 일반 타겟 초당 1,000회 이상 / 가벼운 타겟 초당 10,000회 이상 권장. 초당 10회 이하라면 심각한 성능 문제.
  • 전역 상태(Global State) 최소화: 전역 변수를 수정하면 비결정성을 유발할 수 있어 퍼징 효율이 떨어진다.
  • 타겟은 좁을수록 좋음: JSON, XML, YAML을 하나로 처리하는 것보다 각각 전용 퍼저로 분리하는 것이 훨씬 효율적이다.

Fuzzing vs Fuzzer 차이점

Fuzzing과 Fuzzer는 비슷해 보이지만 명확히 다른 개념이다.

Fuzzing

버그를 찾기 위한 테스트 기법(방법론) 그 자체다. 프로그램에 수많은 입력값을 자동으로 넣어보면서 크래시(Crash), 메모리 오류, 예외 상황, 보안 취약점을 찾아내는 과정 전체를 말한다.

예시: 웹 브라우저에 수백만 개의 이상한 CSS 입력을 넣어보는 행위 자체가 Fuzzing

Fuzzer

Fuzzing을 수행하는 도구(프로그램)다. 입력을 생성하고 변형(Mutation)하며 프로그램을 반복 실행하는 소프트웨어다.

대표적인 Fuzzer: libFuzzer, AFL, AFL++, Honggfuzz

쉽게 비유하면

개념비유 1비유 2
Fuzzing시험 보는 행위낚시
Fuzzer시험 문제를 내는 기계낚싯대

세 개념의 관계

Fuzzer (AFL++, libFuzzer) ↓ 실행 Fuzz Target (LLVMFuzzerTestOneInput 등) ← Fuzzer가 입력을 던지는 대상 ↓ 반복 테스트 Fuzzing (입력 생성 → 실행 → 경로 발견 → 변형 → 반복) ← 버그 탐색 과정 전체
핵심 한 줄 요약: Fuzzing은 소프트웨어의 취약점을 찾기 위해 비정상적인 입력을 대량으로 생성하는 테스트 기법이며, Fuzzer는 이러한 Fuzzing을 자동으로 수행하는 도구다.

🎯 Jackalope

github.com/googleprojectzero/Jackalope →

Google Project Zero(구글 최정예 보안팀)가 만든 Fuzzer. 소스코드 없이 바이너리만으로 Fuzzing 가능하다. 실습용 도구 (Windows/macOS)

  • 소스코드 없이 바이너리 기반으로 Fuzzing하는 방법
  • Windows/macOS 환경에서의 Fuzzing 실습
  • TinyInst 경량 계측(Instrumentation) 라이브러리 동작 원리:

    계측(Instrumentation)이란 프로그램 실행 중에 코드를 추가로 삽입해서 어떤 코드가 실행됐는지 추적하는 기술이다. Fuzzing에서는 "이 입력이 새로운 코드 경로(분기)를 열었는가?"를 판단하기 위해 사용한다.

    TinyInst는 프로세스 전체가 아닌 선택된 모듈만 계측하고 나머지는 네이티브로 실행하는 경량 동적 계측 라이브러리다.즉,소스코드 없이 실행 파일(.exe 등)만으로 원하는 모듈의 실행 흐름을 추적할 수 있다. 동작 방식은 다음과 같다.

    • 계측할 모듈이 로드되면 해당 모듈의 실행 영역을 실행 불가능 상태로 표시한다.
    • 프로그램이 해당 영역을 실행하려고 하면 예외(Exception)가 발생하고, TinyInst 디버거가 이를 가로챈다.
    • 디버거가 원본 코드를 별도 공간에 복사하면서 중간에 추적 코드를 삽입한다.
    • 이후 계측된 코드가 대신 실행되며, 어떤 경로로 실행됐는지 커버리지 정보가 기록된다.

    AFL++은 컴파일 시점에 미리 추적 코드를 삽입하기 때문에 소스코드가 필요하다. 반면 TinyInst는 실행 중에 바이너리를 직접 계측하기 때문에 소스코드 없이도 동작한다. 덕분에 Jackalope은 소스코드가 없는 Windows/macOS 프로그램도 Fuzzing할 수 있다.

  • AFL++과의 아키텍처 차이 비교
